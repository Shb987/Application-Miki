# Core Feature Modules Unpacked

The platform is designed as an amalgamation of distinctly complex standalone systems. This document outlines the deep technical functionality of the primary feature modules within the environment.

## 1. Automated Examination & Evaluation Infrastructure

The educational cornerstone of the application allows for rapid deployment of quizzes and highly complex formal exams.

### 🗃 The Question Bank
Instead of creating static exams, administrators build a categorized **Question Bank**.
*   **Routing Origin:** Supervised via `admin_exam_routes.py`.
*   **Data Structure Structure:** Questions (`question_models.py`) are highly structured. They aren't just strings; they contain explicit mappings to `<Subject>`, `<Grade Level>`, and `<Difficulty>`. They also support multimedia injections (like HTML equations or images).
*   **Usage:** Exams are assembled by pulling references from this giant unified bank.

### 📝 Dynamic Exam Generation
*   When an administrator requests an exam generation, the `exam_service` takes sorting criteria (e.g., 10 Hard Math questions, 5 Easy) and queries the bank.
*   **PDF Pipeline:** Generating exams produces a physical output. The system leverages templates inside the `app/report/` folder to literally script and arrange questions on an exported PDF document utilizing specialized Python PDF layout engines. These are cached statically in `app/static/generated_papers`.

### 🧠 Subjective & Objective Evaluation System
*   **Objective Check:** Multiple-choice questions (MCQs) are evaluated instantly via backend comparisons to the source-of-truth bank.
*   **Subjective Analysis:** Handled via `exam_evaluation_routes.py`. When students submit long-form answers, the platform packages the question, the ideal expected key, and the student's submission. It then ships this payload to an external provider (often an LLM) instructed specifically to act as an impartial grader. The pipeline streams structured validation metrics back (score, constructive feedback, weak areas).

## 2. Server-Side Administrative Interface (SSR)

Instead of maintaining a massive single-page application (SPA) in React or Flutter simply to manage the database, this backend serves its own interactive panel.

*   **Jinja2 Templates:** Located in `app/templates/admin/`. Instead of creating REST APIs for every database interaction, FastAPI compiles the HTML dynamically server-side.
*   **The Controller Flow:** `admin_pages.py` handles the HTTP GET requests for dashboard views. When an Admin requests the "Manage Users" page, the router independently queries the Motor Database for all students, passes that exact context into the Jinja2 template renderer, and outputs a complete HTML file to the browser.
*   **Form Management:** Traditional `<form>` POST actions are submitted straight back to standard REST routers (`admin_routes.py`) which process the changes and trigger an HTTP Redirect back to the rendered templates.

## 3. Artificial Intelligence Integrations

The system leverages advanced large language models (LLMs) to transform static education into an interactive experience. **Crucially, all AI modules implement the `ai_usage_logger` utility to aggressively track token-cost profiles per endpoint.**

### 🤖 The AI Tutor (`ai_tutor_routes.py`)
*   **Scope:** Specifically constrained to academic subject-matter resolution.
*   **Implementation:** Relays structured system-prompts ensuring the AI will not solve equations outright, but rather utilize the Socratic method to lead the student to the answer. It maintains brief conversational memory using `chat_models` schemas.

### 🗣 The Conversational Companion (`companion_routes.py`)
*   **Scope:** Focuses on mental health, study habits, and psychological tracking.
*   **Implementation:** The companion processes long-term "Future Study" vectors generated by the analytics tool to provide custom study schedules and emotional support through a more conversational schema than the strict Tutor module.

### 🎙 Voice Assistant Modules
*   **Scope:** Supports multi-modal accessibility.
*   **Pipeline:** 
    1. Ingestion of Base64 encoded audio blobs.
    2. Transcription (STT) parsing through external services or lightweight offline models.
    3. NLP Intent Processing via `ai_tutor_service`.
    4. Text-To-Speech (TTS) generation to deliver an audible payload back to the student.

## 4. Gamified Engines & Tracking

To capture student interest over time, fully server-side validated games act as engaging palette cleansers to the core educational loops.

### ♜ Native Python Chess (`user_game_chess.py`)
*   Unlike typical implementations that call external `Stockfish` binaries (which are difficult to host in cloud containers safely), this feature utilizes a **Pure Python Chess Engine**.
*   **The Service (`chess_service.py`):** Calculates legal moves via native bitboards or matrix representations. To handle "Bot" actions against players, it evaluates positions using the `Minimax` algorithm, pruning bad paths to simulate difficulty ratings.

### 🟩 Wordle Framework (`user_game_wordle.py`)
*   **Functionality:** Students submit a guess against a daily target. The `verify_wordle.py` internal utility strips the word, validates it against loaded dictionaries (seeded via `seed_wordle.py`), and builds an exact state-array of Green, Yellow, and Gray states.
*   **Streak Management:** The backend modifies the student's `PlayerStats` MongoDB profile, explicitly storing the number of daily consecutive plays and attempts necessary to win, utilizing this for global leaderboards.
